# 실제 체결 기반 모의투자 피드백·보정 계획

작성일: 2026-10-27 KST

## 1. 목적과 현재 상태

향후 실제 주문·체결·취소 기록을 입력하여 모의 체결과의 차이를 분석하고, 대기열·취소 배분·전송 지연·체결 비용 모형을 개선한다. 사용자가 추가할 계획이라고 명시한 후속 기능의 설계다. **이번 변경은 계획·데이터 계약을 문서화한 것이며 업로드, 실제 기록 비교, 자동 보정 실행 기능이 구현된 상태는 아니다.**

현재 구현된 재생기의 계좌별 `initial_config`, 전략 버전, 원본 manifest, 체결별 손익·큐 위치, 난수 시드, `closed_orders`, `end_orders`를 비교 실험의 근거로 활용한다. 실제 자료를 기존 가상계좌 원장에 더하거나 과거 모의체결을 실제 체결로 바꾸지 않는다. 비교 결과와 보정 프로필은 별도 저장하고, 적용하면 새 모의계좌를 만든다.

## 2. 두 가지 실험을 분리

### A. 실제 주문 경로 재생 — 체결 모형 검증

실제로 제출한 주문·취소·교체 의도와 당시 시장 호가·틱을 재생기에 입력한다. 실제 체결 결과는 비교 정답으로만 사용하고 가상 체결을 강제하는 입력으로 쓰지 않는다. 실제로 제출한 의도를 재생하는 동안 전략이 별도 주문을 추가하지 않도록 자동 주문을 끈다.

같은 가격의 복수 주문과 각 부분체결은 주문 식별자로 연결한다. 실제 다음 주문이 앞선 실제 체결 결과에 따라 만들어졌더라도, 이 실험에서는 기록된 다음 의도를 그대로 사용한다. 따라서 이것은 **고정한 주문 경로에 대한 조건부 검증**이며 전략의 독립 수익성 검증이 아니다. 모의 잔고로 해당 의도를 제출할 수 없게 되면 돈을 보충하지 않고 경로 불일치를 기록한다.

### B. 보정 프로필을 사용한 전략 재실행 — 영향 평가

A에서 검증한 체결 모형 후보를 선택한 뒤 전략이 가상 상태에 따라 스스로 주문하도록 새 계좌에서 실행한다. 후보가 체결·재고·손익·헤지에 어떤 변화를 만드는지 기존 모형과 비교한다. 이 단계의 가상 주문은 실제 주문과 1:1 대응하지 않을 수 있다. 실제 PnL에 가까워졌거나 모의 수익이 늘었다는 이유만으로 모형 적합성이 좋아졌다고 판정하지 않는다.

## 3. 자료 수준별 가능한 분석

| 입력 수준 | 가능한 비교 | 제한 |
|---|---|---|
| 실제 체결 목록만 있음 | 체결 가격·수량·비용 집계, 연결된 모의체결과의 제한적 대조 | 체결하지 않은 주문 분모가 없어 체결률·오체결률·취소 모형 보정 불가 |
| 전체 주문 목록·최종 상태·부분체결 | 완료/부분/미체결 비율, 주문별 체결량·취소량 대조 | 요청·응답 시각이 없으면 실제 지연과 취소 경쟁 재현 불가 |
| 주문 생애 이벤트 + 호가·틱 | 고정 주문 경로 재생, 대기시간·부분체결·취소 경쟁 오차 | L2 자료로 실제 외부 큐 위치나 취소 위치는 직접 알 수 없음 |
| 위 자료 + 시계·연결 품질·헤지 연결 | 지연 분포·급등 구간·헤지 소요 시간의 관측 범위 내 비교 | 거래소 도착 시각·native 규칙·부족한 상대 거래소 자료는 여전히 미확인일 수 있음 |

처음에는 사용자가 가진 체결 파일만으로 시작할 수 있게 하되, 부족한 자료가 필요한 분석은 ‘자료 부족’으로 표시한다. 체결 목록에 없는 주문을 자동으로 미체결 주문이라고 생성하지 않는다.

## 4. 수집·입력 데이터 계약

첫 입력 형식은 정규화한 CSV/JSONL 파일과 필드 매핑으로 계획한다. 빗썸·OKX 거래소별 내보내기 원본은 별도 변환 어댑터를 둔다. 파일의 컬럼 이름·ID 범위·단위·시간대는 실제 파일을 받은 뒤 확정한다. 현재 거래소 내보내기 형식을 이미 지원한다고 주장하지 않는다.

### 공통 식별·출처

| 필드 | 내용 |
|---|---|
| `dataset_id`, `revision` | 불변 자료 묶음과 정정 버전 |
| `source_file_hash`, `source_row` | 원본 근거·재입력 검증. 같은 파일의 재입력으로 기록을 중복 반영하지 않음 |
| `venue`, `account_alias`, `market`, `instrument` | 거래소·가명 계좌·현물/선물·종목 구분. 서로 다른 계좌나 시장을 같은 주문으로 합치지 않음 |
| `native_order_id`, `client_order_id` | 거래소 주문 ID와 현지 요청 ID. 없는 필드는 null |
| `event_id`, `event_type`, `native_sequence` | 사건 ID·종류·제공된 거래소 순번. 로컬 부여 순번과 native 순번은 구분 |
| `raw_timestamp`, `raw_unit`, `raw_timezone` | 원래 시각과 해석 근거. 정규화 후에도 보존 |
| `exchange_at_ms`, `local_at_ms`, `observed_at_ms` | 발생·현지 요청/기록·수신 시각. 의미에 맞는 값만 채우며 미관측 값은 null |
| `clock_domain`, `time_quality` | 어떤 시계인지, 시간대·단위·동기화 오차·정밀도 확인 상태 |

공통 필수값은 자료/버전·로컬 사건 ID·사건 종류·거래소·계좌 별칭·시장·종목이다. 주문 비교에는 native 또는 client 주문 ID 중 하나가 필요하다. 체결 행에는 방향·가격·양수 수량·수량 단위가 필요하며, 미제공 수수료·역할·시각은 null로 둔다. Native trade ID가 없으면 원본 행 기반 키를 사용하되 파일 간 중복 여부는 미확인으로 표시한다.

복합 주문 키는 `(venue, account_alias, market, instrument, native_order_id)`를 기본으로 한다. 주문 ID 없이 client ID만 있으면 별도 이름공간의 임시 키로 보관하고 확인 후 연결한다. 체결 고유 키는 해당 주문 키와 native trade ID를 결합한다. 실제 원본의 고유성 범위가 확인되기 전에는 ID만으로 전 계좌·전 종목을 중복 제거하지 않는다.

### 주문 생애 이벤트

`submit`, `ack`, `reject`, `cancel_request`, `cancel_ack`, `cancel_reject`, `replace_request`, `amend_ack`, `expire`, `status_snapshot`을 구분한다. 각각 제공된 원본만 기록한다.

- 매수/매도, 주문 유형·TIF·STP, 한도가격, 요청 총수량, 누적 체결량, 남은 수량, 종료 사유.
- native 정정의 수량이 총수량인지 남은 수량인지 명시한다. 취소 후 신규 ID와 같은 ID의 native 정정을 구분한다.
- 전략 ID·버전·설정, 원래 의도 그룹/슬롯/revision, 원주문/교체 주문 연결이 있으면 보관한다.
- 제출 실패와 거래소 거절, 취소 요청과 취소 확정, 실제 발생과 통지 수신을 서로 대체하지 않는다.
- 관측 시작 전부터 살아 있던 주문, 관측 종료 때 아직 살아 있는 주문, 로그가 끊긴 주문을 구분한다.

### 실제 체결 이벤트

- `native_trade_id`, 주문 키, 실제 체결 가격·부분체결 수량, 제공된 maker/taker 역할.
- 수량 단위는 코인 수량 또는 계약 수를 명시한다. 계약 배수·규격·유효 기간이 없으면 OKX 계약 수를 코인으로 임의 변환하지 않는다.
- 수수료 금액·통화, 리베이트, 거래소가 제공한 실현손익과 그 통화를 원본 그대로 보관한다. 평가환율·원가 방식이 맞지 않으면 원화 손익을 직접 비교하지 않는다.
- 체결 정정·취소(bust)가 들어오면 원본을 덮지 않고 정정 사건과 새 자료 버전으로 연결한다.
- 가격·수량·금액은 십진 문자열로 정규화한다. 실제 리베이트가 음수여도 원본을 버리지 않는다. 현재 재생기의 비음수 수수료 모형과 맞지 않으면 지원 제한을 표시한다.

### 시장·초기 계좌·연결 자료

- 해당 기간의 호가·틱과 원본 manifest/해시, 소스 시각 기준, tick 공격 방향·단위, 기록 범위·연결 상태.
- 비교 시작 시 현금·코인·평균 원가, 이미 열린 주문, 선물은 포지션·담보·계약 규격이 필요하다. 초기 원가가 없으면 체결 비교는 하되 실현손익 대사는 미평가로 둔다.
- 입출금·이체·펀딩·수수료 조정 등 거래 외 원장 사건은 별도 기록한다. 이를 체결 모형의 오차로 흡수하지 않는다.
- 헤지를 비교하려면 원체결 ID와 hedge group/주문 배분, 여러 원체결의 합산 여부, 실제 헤지 체결 연결이 필요하다.

다음은 **예시 계약**이며 실제 계좌·실주문 자료가 아니다. null은 미관측값이다.

```json
{
  "dataset_id": "example-only",
  "revision": 1,
  "event_type": "fill",
  "event_id": "example-fill-1",
  "venue": "bithumb",
  "account_alias": "example-account",
  "market": "spot",
  "instrument": "BTC/KRW",
  "native_order_id": "example-order-1",
  "client_order_id": null,
  "native_trade_id": "example-trade-1",
  "side": "buy",
  "price": "100000000",
  "quantity": "0.001",

```

이 예시의 두 시각 차이 20ms를 곧바로 순수 전송 지연으로 학습하지 않는다. 시계 정합 확인이 먼저다.

## 5. 정규화·대사 규칙

1. 업로드 자료에 해시·원본 행 번호를 부여하고 원본을 보존한다. 필드 매핑과 단위·시간대 설정도 버전으로 남긴다.
2. 같은 파일·같은 원본 행 재입력은 멱등 처리한다. 다른 파일의 같은 사건은 신뢰 가능한 native ID와 내용이 일치할 때만 연결한다. 동일 시각·가격·수량만 같다는 이유로 서로 다른 체결을 삭제하지 않는다.
3. 동일 고유 ID의 내용이 다르면 충돌로 격리한다. 최종 상태 스냅샷에 포함된 누적 체결을 이미 가져온 개별 체결과 다시 합산하지 않는다.
4. 주문별 요청량, 확정 체결량, 취소/거절량, 잔량을 대사한다. 과체결·음수 잔량·상태 역전·누락된 원주문을 검출한다. 정정 계약 없이 변경된 총수량을 소급 적용하지 않는다.
5. 실제와 모의 주문은 명시적 연결 키 또는 제출 의도 연결로 매칭한다. 가격·시각 근접 매칭은 후보만 만들고 확정된 주문 대응처럼 쓰지 않는다. 같은 가격 복수 주문을 하나로 합치지 않는다.
6. 부분체결 개수가 달라도 주문별 누적 수량 곡선·최종량·VWAP를 비교할 수 있다. 원본의 여러 부분체결을 편의상 하나로 바꾸지 않는다.
7. 충돌·누락·시계 불명확·자료 공백·미지원 주문은 제외 사유와 수량을 기록한다. 비교 가능한 표본만의 성능과 전체 자료 대비 커버리지를 함께 제시한다.

## 6. 시간 정렬과 실제 시장에 남은 내 주문

UTC epoch ms로 정규화하되 원래 시간 정밀도와 native 순번을 보존한다. ms보다 정밀한 자료를 재생기에 맞춰 축약하면 동률 발생·순서 불확실성을 표시한다. 시계 offset·변동을 추정하는 규칙은 별도 설정이며, 목표 체결 결과를 보고 임의로 시각을 움직여 오차를 없애지 않는다.

같은 로컬 시계의 `ack 수신−submit 전송`은 요청부터 응답까지의 관측 지연이다. 거래소 처리 시간을 포함할 수 있으며 거래소 도착 시각이나 순수 네트워크 RTT를 알려 주지 않는다. 이를 반으로 나눠 주문 도착 지연으로 확정하지 않는다. `desk−server` 시간차도 같은 이유로 구분한다. 다른 시계 간 차이는 동기화 근거·오차 범위가 있어야 별도 지연 추정에 사용할 수 있다.

실제 거래 당시 내 주문은 이미 원본 공개 호가·틱에 영향을 주었을 수 있다. 같은 주문을 가상으로 다시 추가하면 내 공개 잔량을 외부 큐로 두 번 세거나 내 실제 체결을 다시 기회로 사용할 수 있다. private 주문/체결과 public 행의 확정 연결이 있을 때만 명시적 조정 어댑터를 적용하고 조정 전후를 보존한다. 공개/비공개 체결은 별개 원장 사건으로 중복 합산하지 않는다. 연결이 불가능하면 `own_impact_unknown`으로 표시하고 완전한 무시장영향 검증이라고 주장하지 않는다.

## 7. 비교 지표

기본 비교 단위는 거래소·종목·주문·평가 기간이다. 매수/매도, TIF, maker/taker, 유동성·스프레드·변동성·시간차 구간도 함께 분리한다.

| 지표 | 계산·표시 원칙 |
|---|---|
| 주문 대응·평가 커버리지 | 전체/정상화/정확히 대응/평가 가능/제외/미해결 건수와 사유 |
| 체결 여부 혼동표 | 같은 평가 창에서 실제/모의 체결 있음·없음을 비교. 두 쪽 모두 관측이 완결된 주문만 음성으로 판정 |
| 수량 오차 | 모의 누적 체결량−실제 누적 체결량, 절대 오차와 요청량 대비 비율 |
| 시간별 누적 체결 비율 | 초기 후보는 제출 후 1초·10초·60초 및 종료 시점. 해당 시점까지 충분한 관측이 있어야 비교 |
| 첫 체결·전체 완료 시간 | 두 쪽 모두 완료된 표본의 오차와 해당 커버리지를 표시. 미완료·관측 종료는 0초로 넣지 않음 |
| 미체결·취소 전후 경합 | 취소 요청 후 추가 체결량, 취소 확인까지 시간, 부분체결 뒤 취소 비율 |
| 가격·비용 오차 | 체결량과 VWAP를 함께 표시. maker/taker 수량·수수료 통화·환산 근거를 분리 |
| 결과 상태·수량 분해 | filled/live/cancelled/rejected/unknown의 차이. 모델 unknown을 실제 미체결로 취급하지 않음 |
| 여러 시드의 결과 분포 | 체결량·대기시간 분포와 실제 관측값의 위치, 예측 구간 커버리지. 하나의 운 좋은 시드를 채택하지 않음 |
| 헤지 비교 | 연결된 원체결→통지/응답/첫 헤지/완료 시간, 미헤지 지속 시간·수량. 각 시각의 관측 가능 여부 표시 |

관측 시작 전에 이미 제출된 주문은 시작부터의 대기시간을 안다고 가정하지 않는다. 기간 끝까지 살아 있는 주문은 우측 검열로 다루고 ‘영구 미체결’로 학습하지 않는다. 자료 누락으로 끝난 경우와 정상 취소로 종료된 경우도 분리한다. 확률 지표는 평가 창·완결된 표본·시드 집합을 고정한 경우에만 산출한다. 검열 처리를 구현하지 않은 초기 버전은 해당 지표의 평가 가능 집합과 제외율을 먼저 보고한다.

## 8. 보정 대상과 식별 한계

| 대상 | 사용할 근거 | 현재 실행기와의 관계 |
|---|---|---|
| `queue_cancel_bias` | 미체결을 포함한 주문별 누적 체결·대기시간 오차 | 현재 설정값. 실제 앞쪽 취소 위치의 직접 측정값은 아님 |
| `queue_cancel_chunks` | 여러 주문에서 부분체결·대기시간 분산과 후보 모형 분포 | 현재 설정값. 실제 주문 개수나 취소 덩어리 수로 해석하지 않음 |
| `latency_ms`, `cancel_ack_policy` | 요청·응답·취소 경합 로그에서 관측 가능한 지연과 정책 | 현재 주문·취소 공통 지연. 각 경로의 다른 분포를 적용하려면 실행기 확장이 필요 |
| `max_feed_delay_ms`, 급증·재개 조건 | 시세 시간차·주문 거절·수신 품질의 함께 관측된 구간 | 현재 설정값. 적용 후 어떤 주문을 냈을지는 전략 재실행에서 평가 |
| maker/taker 수수료 | 실제 역할·체결 대금·수수료 통화·리베이트 | 현재 비음수 bp 모형과 맞는 구간만 변환. 별도 비용을 수수료율에 억지 흡수하지 않음 |
| 헤지 단계별 지연 | 원체결·통지·전송·응답·헤지 체결의 연결 | 단계별 기록 계약은 있으나 OKX 헤지 실행은 아직 연결 전 |
| 초기 큐 여유·숨은 유동성·변동 지연 분포 | 충분한 주문 표본과 별도 모형 검증 | 후속 확장 후보. 현재 설정처럼 표시하거나 적용하지 않음 |

초기 앞 물량, 전송 지연, 취소 배분은 서로 비슷한 체결 결과를 만들 수 있다. 실제 체결만으로 이 값을 각각 유일하게 알아낼 수는 없다. 여러 후보가 비슷하면 가능한 범위와 비식별성을 보고하고 임의로 하나를 실제값이라고 확정하지 않는다. 수익을 맞추기 위한 사후 가격 조정·특정 주문 예외·최고 성과 시드 선택은 보정 방법으로 사용하지 않는다.

## 9. 피드백 절차와 버전

`실제 자료 등록 → 정규화·품질 대사 → 주문 경로 연결 → 현재 모형 재생 → 차이 보고 → 보정 후보 생성 → 별도 기간 검증 → 새 프로필 선택 → 새 모의계좌 평가` 순서로 진행한다.

1. 자료·필드 매핑·시간 정렬·시작 상태·주문 대응·원본 시장 데이터 버전을 고정한다.
2. 후보를 만들기 전에 시간순 학습/선택/최종 평가 구간을 분리한다. 잠정 비율은 60/20/20이며 주문 생애가 경계를 넘으면 경계 표본으로 격리한다. 경계 뒤의 결과를 앞 구간 학습 라벨로 사용하지 않고, 서로 다른 부분체결을 양쪽에 나누지 않는다. 후속 구간에서 온전한 평가가 가능한지는 별도로 판정한다. 실제 기간과 표본 수가 부족하면 정식 보정 대신 탐색 비교로 표시한다.
3. 탐색할 파라미터 범위·시드 집합·비교 지표·평가 창을 먼저 고정한다. 모든 후보는 같은 시장·의도·시드 집합으로 비교한다. 원본 밖의 값이나 NaN을 허용하지 않는다.
4. 학습 구간에서 후보를 만들고 선택 구간에서 검토한다. 최종 평가 구간을 반복 보며 조정했다면 그 구간은 더 이상 미사용 평가가 아니므로 새 평가 기간을 확보한다.
5. 전체 평균뿐 아니라 종목·시간대·변동성·TIF별 성능과 악화 구간, 표본 수·검열·제외율을 비교한다. 주문 수가 적다는 이유로 근거 없는 높은 신뢰도를 표시하지 않는다.
6. 처음에는 보정 후보와 보고서만 생성한다. 사용자가 후보를 선택하면 새로운 불변 실행 프로필로 저장하고 이후 새 계좌에 적용한다. 진행 중 실행·과거 결과·기본 전략 버전을 자동으로 덮어쓰지 않는다.
7. 새 실제 자료가 들어오면 현재 프로필의 드리프트와 후보 성능을 다시 평가한다. 과거 보정 버전·적용 계좌·평가 근거를 추적하고 이전 프로필을 다시 선택할 수 있게 한다.

새 프로필에는 `parent_profile_id`, 데이터/매핑/매칭/시간 정렬 버전, 코드 revision, 모형 버전, 파라미터, 시드 집합, 학습/평가 구간, 지표·평가 가능 수, 제외 사유·한계, 생성/선택 시각을 보존한다. 이름만 같은 새 파일로 이전 결과를 바꾸지 않는다.

## 10. 후속 모듈·저장·화면 계약

다음 위치와 API는 **제안**이며 현재 파일·엔드포인트가 구현됐다는 뜻이 아니다. 모듈 경로는 `oms_client/` 기준이다.

| 제안 모듈 | 책임 |
|---|---|
| `execution_feedback/importers.py` | 파일 해시·형식 감지·거래소별 필드 매핑·단위 확인 |
| `execution_feedback/normalization.py` | 정규화 사건·ID 범위·정정·멱등성·품질 판정 |
| `execution_feedback/alignment.py` | 시간 정렬·주문 대응·부분체결 연결·관측 공백 |
| `execution_feedback/order_replay.py` | 실제 제출 의도를 가상 시각에 주입. 실제 체결은 정답으로만 격리 |
| `execution_feedback/comparison.py` | 주문별 누적 곡선·상태·수량·시간·비용 오차와 커버리지 |
| `execution_feedback/calibration.py` | 고정 구간/시드의 후보 탐색·검증·비식별성·드리프트 보고 |
| `execution_feedback/profiles.py` | 보정 후보·선택 프로필 버전·계좌 연결·이전 버전 선택 |
| `execution_feedback/store.py` | 실제 사건·비교·실험 계보를 가상계좌 원장과 분리 저장 |

저장 엔터티는 `execution_datasets/revisions`, `raw_rows`, `normalized_events`, `quality_issues`, `order_links`, `comparison_runs/order_metrics`, `calibration_candidates`, `execution_profiles`로 나눈다. 자료 정정은 새 revision, 비교 재실행은 새 run이다. 같은 자료를 두 번 가져와도 경제적 사건이 두 번 생기지 않아야 한다.

화면은 **실제 거래 피드백**에서 자료 등록·필드 매핑·문제 행 확인 → 실제/모의 주문 타임라인·누적 체결량·대기시간·오차 표 → 보정 전후 비교·평가 기간·제외율 → 새 프로필로 계좌 준비 흐름을 제공한다. 주문별 타임라인에는 실제 발생/수신, 모의 사건, 비교 불가 구간을 구분한다. ‘미체결’, ‘자료 없음’, ‘아직 평가 시점 전’을 같은 0으로 표시하지 않는다.

API 제안은 자료 등록/검증, 비교 생성/조회, 보정 후보 생성/조회, 프로필 목록/선택이다. 현재 `/api/replays`나 실제 거래소 주문 API에 가져온 체결을 직접 반영하는 경로는 만들지 않는다. 작업 큐와 취소·진행률·결과 저장은 기존 서버 작업 패턴을 재사용할 수 있다.

## 11. 단계별 완료 조건

| 단계 | 완료 조건 |
|---|---|
| 1. 수입·정규화 | 재입력 멱등성, ID 충돌, 시각/단위 오류, 정정, 부분체결·계좌 분리가 검증됨 |
| 2. 경로 재생·비교 | 실제 체결 강제 주입 없이 고정 의도를 재생하고, 주문 대응·미체결/취소/공백·검열과 지표를 구분함 |
| 3. 후보 보정 | 같은 데이터·범위·시드에서 재현되며 분리 평가 구간으로 성능·악화·커버리지를 보고함 |
| 4. 버전 적용 | 새 프로필을 새 계좌에만 적용하고 원본·이전 결과·진행 실행이 바뀌지 않음 |
| 5. 반복 피드백 | 새 자료에서 드리프트·재보정 후보·이전 버전 대비 결과를 추적함 |

검증 fixture에는 전체 미체결 주문, 여러 부분체결, 취소 중 체결, 같은 가격 복수 주문, native ID 충돌/재입력, 음수 리베이트, 계약 단위 누락, 시계 offset, 수신 역전, 관측 시작/종료 경계, 자료 공백, 실제 주문의 public 영향, 학습/평가 경계 주문을 포함해야 한다. 실제 기록을 가져왔다고 자동으로 지정가 142개 미지원 항목이 구현된 것으로 바꾸지 않는다. 실행 가능 범위는 [지정가 대조표](limit_execution_coverage.ko.md)를 따른다.

잠정 결정은 [Q-011~Q-013](strategy_registration_queries.ko.md)에 기록한다. 실제 자료를 받을 때 형식과 관측 가능한 범위를 확인하여 이 계약의 새 버전으로 구체화한다.
