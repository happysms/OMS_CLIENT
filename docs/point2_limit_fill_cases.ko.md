# 모의투자 지정가 체결 경우의 수와 처리 제안

작성일: 2026-10-26 KST\
상태: 설계·검증 시나리오 목록. 현재 항목별 구현·가정·미지원 상태는 [실행 대조표](limit_execution_coverage.ko.md)를 따른다. 목록 전체의 구현 완료나 현실 체결 확률을 뜻하지 않는다.\
상위 문서: [전체 구상](point2_replay_design.ko.md), [모듈 상세 명세](point2_replay_modules.ko.md)

계좌 초기조건·주문 후 자산 변화: [가상계좌 생성과 시뮬레이션](point2_virtual_accounts.ko.md). 아래 체결 사례는 고정 초기조건에서 생성한 실행별 계좌에 적용한다. 다른 run의 잔고를 공유하지 않는다.

## 1. 적용 범위와 분류 방법

한 모의투자 실행에는 **서로 다른 거래소 1~2개**를 선택한다. 초기 어댑터는 빗썸 현물과 OKX 선형 USDT 선물이다. 3개 이상, 중복 거래소 항목, 선택하지 않은 거래소의 입력·주문은 실행 전 검증에서 거절한다. 종목·매수/매도·계좌 통화는 거래소 개수에 포함하지 않는다. 빗썸 CT와 빗썸 USDT는 같은 거래소다.

거래소 하나로 실행할 수 있는 엔진과, 특정 전략이 요구하는 거래소 조합은 구분한다. 원본 point2의 OKX 기준가격·현물/선물 헤지 프로필에는 빗썸·OKX가 모두 필요하다. 하나만 선택하면 그 프로필은 검증에서 차단한다. 단일 거래소용 프로필에서 임의로 두 번째 거래소를 생성하지 않는다.

각 거래소는 여러 매수·매도 주문을 동시에 유지할 수 있다. 같은 가격의 여러 order_id와 여러 가격의 호가를 모두 지원한다. 하나의 시계에서 재생하되 호가·공유 대기열·거래량 예산·주문·잔고·규격은 거래소별로 분리한다.

가격과 시각을 연속해서 바꾸면 주문의 전체 생애 경로는 무한히 많다. 따라서 여기서 “모든 경우”는 **접수, 도착 가격, 가능 수량, 주문 조건, 대기열 사건, 변경 경합, 계좌, 통지, 데이터 품질, 종료**의 독립 분기를 빠짐없이 조합하는 것을 뜻한다. 아래 12개 묶음·142개 사례는 그 분기와 경계값의 검증 목록이다. 각 행이 서로 배타적인 최종 상태라는 뜻은 아니며 한 주문이 여러 행을 순서대로 경험할 수 있다.

기본 엔진은 연속매매·L2 snapshot과 체결 틱·GTC/IOC/Post-only를 대상으로 한다. FOK·조건부 주문·만료·경매 등은 L 묶음에서 확장 경계로 구분한다. 실제 거래소의 특수 규칙은 해당 시점·계좌 모드의 프로필로 고정한다.

## 2. 체결 결과의 기본 분해

```text
Q = F + W + C + R + U
W = in_flight + live
F = 확정 taker 수량 + 확정 maker 수량

Q: 요청수량   F: 확정 체결   W: 전송 중·대기
C: 확정 취소  R: 접수 거절   U: 모형이 판정하지 못한 수량
```

| 기본 결과 | 수량 상태 | 의미 |
|---|---|---|
| 전송 중 | in_flight=Q | 아직 거래소에 도착하지 않음 |
| 접수 거절 | R=Q, F=0 | 규격·잔고·담보·거래 상태 등으로 거절 |
| 미체결 대기 | live=Q | 접수됐으나 체결 없음 |
| 부분체결 대기 | 0<F<Q, live=Q−F | 확정 체결 뒤 남은 양은 계속 유효 |
| 전량 체결 | F=Q | 한 번 또는 여러 fill로 완료 |
| 미체결 취소 | C=Q | 체결 없이 취소·조건 종료 |
| 부분체결 뒤 취소 | 0<F<Q, C=Q−F | 체결은 유지하고 잔량만 취소 |
| 판정 불가 포함 | U>0 | 자료·깊이·단위·순서 등의 부족 |

기본 단일 주문은 전량 접수 또는 전량 거절이다. 이미 체결된 뒤 남은 양이 종료되는 것은 R이 아니라 C다. 배치 일부 거절은 child별 결과로 기록한다. 수량 변경·부분 접수 등 다른 native 계약은 별도 프로필이 필요하다.

**U는 거래소 취소 상태가 아니다.** 엔진이 멈추거나 MODEL_UNKNOWN을 기록해도 실제 가상 경로의 남은 위험·예약이 확정적으로 없어진 것은 아니다. 마지막 확정 상태, 미확인 범위, 잠재 노출을 보존한다. 통지 지연 때문에 전략만 모르는 상태는 observed 지연이며, 엔진 자체가 판정하지 못한 U와 분리한다.

## 3. 도착 시 핵심 체결 행렬

모든 검사는 전송 시각이 아니라 **주문 도착 시각의 가상 거래소 상태**로 한다. 매수는 `limit >= 실행 가능한 best ask`, 매도는 `limit <= 실행 가능한 best bid`일 때 공격 가능한 후보가 된다. 자기 체결 방지·규격·잔고·가격 보호 검사를 함께 통과해야 한다.

| 도착 상태 | 일반 지정가 GTC | 지정가 IOC | Post-only |
|---|---|---|---|
| 비교차·즉시 가능량 0 | 전량 대기 | 전량 취소 | 전량 대기 |
| 교차·가능량 일부 | 일부 taker, 알려진 잔량 대기 | 일부 taker, 확정 잔량 취소 | 조건 취소, 체결 0 |
| 교차·가능량 전량 이상 | 전량 taker | 전량 taker | 조건 취소, 체결 0 |
| 여러 상대 호가에 나눠 존재 | 한도가격 안에서 가격별 소진 | 한도가격 안에서 소진 후 잔량 취소 | 교차이면 조건 취소 |
| 최심부 밖 존재 여부 미확인 | 확정 부분 보존, 나머지 U | 확정 부분 보존, F/C를 모르는 양 U | 교차 확인 가능하면 조건 취소, 교차 자체 미확인이면 U |
| raw 표시는 교차하나 유효 잔량 없음/미정합 | raw만으로 fill 생성 금지 | raw만으로 fill 생성 금지 | 가상 truth의 교차 판정 근거 확인, 불충분하면 미확인 |

limit은 허용 가능한 최악 가격이다. 공격 매수는 그 이하의 상대 매도 가격에서, 공격 매도는 그 이상의 상대 매수 가격에서 체결될 수 있다. 기본 대기 체결 모형의 maker 가격은 내 대기 지정가다.

Post-only의 도착 직후 taker 체결, 정상 IOC 도착 처리 뒤 live 잔량, limit 밖 체결은 기본 모형에서 허용하지 않는다. 일반 GTC는 한 주문 안에서 즉시 taker와 후속 maker가 섞일 수 있다.

매수 대기 후보는 매도 주도 tick에 대해 `buy_price>=trade_price`, 매도 대기 후보는 매수 주도 tick에 대해 `sell_price<=trade_price`다. 후보라는 것은 자동 체결이라는 뜻이 아니다. 더 우선한 물량과 전체 tick 예산 검사를 통과해야 한다.

| K06 | heartbeat/연결 기록으로 확인된 자료 공백 | 영향 주문·포지션에 U/품질 전파, strict 중단 |
| K07 | 단순히 한동안 tick이 없음 | 무체결을 수집 공백으로 자동 단정하지 않음 |
| K08 | 늦은 tick으로 정합 창이 지난 감소가 설명됨 | 과거 체결·큐를 몰래 재작성하지 않고 영향 플래그 |
| K09 | snapshot 반복·증가 때 self 부채와 public 부채를 혼동 | 내 소진은 원본 감소로 소거하지 않음, 이중 보충 금지 |
| K10 | top-N 이탈인지 실제 가격대0인지 모름 | 큐·생명주기 초기화 금지, 관측 범위 상태 보존 |
| K11 | 동시각 교차 스트림 순서가 실제로 미확인 | 고정 순서와 대체 순서 비교, 실제 선후를 안다고 표시 안 함 |
| K12 | 과거 규격·평가가격·환율 중 필수 정보 미확인 | 허용 가정 표시/실행 차단, 손익·노출을 임의0으로 채우지 않음 |

### L. 종료·선택 확장·지원 경계 — 10개

| ID | 경우 | 처리 제안 |
|---|---|---|
| L01 | 평가 종료 때 주문 live/in-flight/cancel-pending | 상태·예약·미통지 fill·미완료 헤지 보존, 미래 체결로 완료 안 함 |
| L02 | 사용자가 pause/stop | 시계/작업 제어만 수행, 자동 거래소 취소·청산으로 바꾸지 않음 |
| L03 | FOK 지정가 확장, 알려진 깊이로 전량 가능/불가 | 전량 즉시체결 또는 전량 조건 취소. 부분체결·대기 금지 |
| L04 | FOK 전량 가능 여부를 깊이 밖이라 모름 | 부분 fill 먼저 commit하지 않음. 원자성 보존하며 판정 불가 처리 |
| L05 | GTD/거래소 만료 기능 확장 | expiry 이벤트의 정확한 효력시각과 fill 경합 정의, 미지원이면 선택 거절 |
| L06 | stop-limit/조건부 지정가 확장 | trigger 전에는 대기 지정가 아님. trigger 후 신규 도착·TIF 분기로 진입 |
| L07 | 경매·단일가·세션 전환 | 연속매매 FIFO를 그대로 적용하지 않고 별도 모형 또는 미지원 |
| L08 | iceberg/숨은 수량/우선순위가 관측되지 않음 | 초기 큐 여유 등 명시된 가정·민감도, 실제 순번 확정 주장 금지 |
| L09 | OCO/조건 연동 주문 확장 | 한 leg fill→다른 leg 취소의 지연·원자성 계약을 별도 정의. 자동 양쪽 체결 방지 보장 금지 |
| L10 | 강제청산·거래소 시스템 취소·규격 변경 | 확인된 사건과 모형이 있을 때 반영, 없으면 미지원/중단·불확실 처리 |

L03~L10은 확장 시 고려할 경우이며 현재 지원 구현을 뜻하지 않는다. 거래소·주문 조합이 지원되지 않으면 설정 단계에서 거절한다.

## 5. 반드시 손으로 확인할 수치 예시

### 5.1 같은 도착 주문의 조건별 분기

```text
관측 ask: 100원×4개, 101원×6개, 다음 가격은 101원보다 높음으로 확인
내 주문: 매수 7개, limit=100원

GTC       → 100원 taker 4개 + 100원 매수 대기 3개
IOC       → 100원 taker 4개 + 잔량 취소 3개
Post-only → 교차이므로 체결0 + 조건 취소7개
```

### 5.2 대기열의 경계값

```text
외부 앞 1,000개 → 내 O1 200개 → 내 O2 100개
반대 거래량800: 외부 앞200, 내 fill0
추가 거래량200: 외부 앞0, 내 fill0
추가 거래량250: O1 fill200, O2 fill50, O2 live50
```

명시한 외부 앞 물량 외에 더 우선한 가격대 물량이 없고 큐 불확실성도 없는 합성 fixture다. 각 tick의 전체 예산은 한 번만 배분한다.

### 5.3 취소 지연 중 부분체결

```text
내 주문 잔량100
t=10 취소 전송, 취소 지연40ms → t=50 효력
t=30 유효 반대 tick으로40개 체결
t=50 남은60개 취소
t=60 새 tick → 이 주문 추가체결0
결과: F40+C60. 늦은 fill 통지가 와도 F40을 다시 더하지 않음.
```

### 5.4 헤지 목표가 사라져도 남는 지정가 위험

```text
현물 매수30 체결 → OKX 매도30 지정가 live
현물 매도30 체결 → 순현물0, 헤지 목표0
OKX 매도 취소 요청 전송 → 아직 효력 전
OKX 매도30 체결 → 실제 선물 숏30이 남음
취소 응답/체결 관측 대사 → 필요한 매수 조정량 재계산
```

목표가 0이 됐다는 이유로 기존 주문·약정을 지우면 마지막 숏30을 누락한다. 반대 매수 조정을 취소 확인 전에 동시에 넣는 정책은 양쪽 도착·체결 순서까지 검사해야 한다.

## 6. 로그와 구현 판단 순서

주문 하나를 단일 “체결 종류” 문자열로 저장하지 않는다. 최소 필드는 다음과 같다.

```text
venue, instrument, side, order_id, order_group_id, quote_slot_id, plan_revision
order_type, tif, limit_price, requested_qty
in_flight_qty, live_qty, maker_filled_qty, taker_filled_qty
canceled_qty, rejected_qty, execution_unknown_qty
sent/arrived/cancel_effective time, event_seq, causal_round
fill_id, fill_price, fill_qty, fee_currency, fee_amount
원본 이벤트·큐 위치·규격·소진/정합 근거
truth/observed entity version, account projection coverage
terminal reason, uncertainty scope, hedge allocation/link
```

판단 순서는 **구성·규격 → 도착시각 → truth 자금/담보 → STP·가격 보호 → 주문 조건 → 즉시 소진 → 잔량 대기/취소/미확인 → 후속 큐 배분 → 원장/통지 → 헤지**다. 프로필상 STP/Post-only 검사 순서가 결과에 영향을 주면 그 순서도 명시한다.

한 이벤트에서 주문·큐·잔고·수수료·예약·후속 통지 예약을 한 번 확정한다. 모든 경우에 수량 합계, 원본 거래량 예산, 잔량 재사용 금지, fill 중복 금지, 미래 정보 금지를 검증한다.

## 7. 검증 조합 제안

각 사례를 가능한 거래소·매수/매도 방향으로 대칭 적용하고, 관련 TIF에만 조합한다. 불가능한 조합은 실패 경로로 확인한다. 예를 들어 Post-only의 도착 직후 taker fill이나 IOC의 정상 처리 뒤 live 잔량은 기대 결과가 아니라 버그 검출 조건이다.

1. 작은 합성 데이터에서 B·C·E의 수량 경계값을 먼저 고정한다.
2. 같은 가격/다른 가격 복수 주문과 양방향으로 확장한다.
3. OKX 계약·reduce-only·다중 지정가 헤지와 목표 변경을 추가한다.
4. 통지 지연·역전·공백·top-N·U를 결합한다.
5. 같은 원본·명령을 배치 크기·pause 횟수·화면 갱신 빈도만 바꿔 재실행한다.

이 목록은 테스트 설계다. 142개 테스트가 현재 구현되거나 실행됐다는 뜻은 아니다. 경제적 결과를 바꾸는 모형 선택과 단순 표시·처리속도 차이를 분리해 검증한다.

## 8. 1차 자료와 프로젝트 가정

현재 주문 조건·native 상태의 확인 기준은 [빗썸 주문 요청](https://apidocs.bithumb.com/reference/주문-요청)과 [OKX 주문 API](https://www.okx.com/docs-v5/en/#order-book-trading-trade-post-place-order)다. 일부 체결 뒤 취소가 있는 주문을 native 상태 이름 하나로 전량 체결이라고 해석하지 않는다. 과거 시점의 규칙·계좌 모드와 현재 문서는 별도 확인 대상이다.

가격별 공유 큐, 관측 tick 예산, self/public 소진 부채, 큐 여유량, 미확인 범위 전파, 같은 ms 순서, 20/40ms 지연은 이 프로젝트의 재생 모형·설정이다. 실제 주문 로그로 보정된 체결 확률이나 정확한 외부 주문 순번을 뜻하지 않는다.
